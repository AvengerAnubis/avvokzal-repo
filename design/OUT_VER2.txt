[level1]2 ПРАКТИЧЕСКОЕ ОБОСНОВАНИЕ РАЗРАБОТКИ

[level2]2.1 Проектирование системы

Проектирование информационной системы «АВ-Вокзал» начинается с определения архитектурных решений, обеспечивающих масштабируемость, безопасность и удобство сопровождения. Система спроектирована по трёхзвенной клиент-серверной архитектуре, разделяющей презентационный слой (фронтенд и мобильное приложение), слой бизнес-логики (бэкенд API) и слой хранения данных (PostgreSQL^[13]). Такое разделение позволяет независимо развивать каждый компонент и масштабировать систему горизонтально.
На этапе проектирования формируется перечень функциональных требований для каждой роли. Пассажиры получают возможность поиска маршрутов, бронирования и оплаты билетов, управления избранными маршрутами и хранения электронных билетов. Администраторы управляют маршрутами, рейсами и учётными записями. Водители просматривают назначенные рейсы и общаются с операторами через чат. Операторы мониторят задержки и корректируют расписание. Use Case Diagram представлен на рисунке 10.
Архитектура API построена по принципу REST^[18] с использованием стандартных HTTP-методов. Каждый ресурс (пользователи, маршруты, рейсы, бронирования, билеты, платежи, чат, задержки) имеет собственный набор конечных точек. Данные передаются в формате JSON, ошибки возвращаются с соответствующими HTTP-кодами. Ролевая модель включает четыре роли, проверка прав выполняется на двух уровнях: на сервере через JWT-гарды NestJS^[10] и на клиенте через middleware NextJS^[11]. Схема ролевой модели представлена на рисунке 11.
Процесс аутентификации основан на JWT^[7]. При регистрации нового пользователя выполняется проверка уникальности адреса электронной почты, хеширование пароля с использованием библиотеки bcrypt и создание записи в базе данных. При входе в систему выполняется верификация пароля, проверка активности аккаунта и при успехе — генерация JWT-токена. Токен содержит идентификатор пользователя, адрес электронной почты и роль, передаётся в заголовке Authorization каждого запроса и проверяется сервером. Диаграмма последовательности аутентификации показана на рисунке 12. Пользовательские интерфейсы проектируются с PrimeReact^[14], что обеспечивает единообразие визуального стиля.
Система чата между водителями и операторами спроектирована на основе модели хранения сообщений в базе данных с флагом прочтения. Каждое сообщение содержит идентификатор отправителя, его роль и текст, что позволяет отслеживать историю переписки. Поддержка статусов чата (ожидание оператора, активен, закрыт) обеспечивает контроль над текущими сеансами связи. Модель данных чата отражена на рисунке 13.
Система отслеживания задержек рейсов создаёт записи с привязкой к конкретному рейсу. При создании записи о задержке статус рейса автоматически изменяется на DELAYED, что инициирует обновление информации на всех клиентских устройствах. Оператор может скорректировать время отправления и прибытия, после чего статус возвращается в SCHEDULED. Диаграмма состояний рейса представлена на рисунке 14.
Процесс бронирования и оплаты определяет последовательность операций: выбор маршрута, создание бронирования, оплата, подтверждение и генерация электронного билета с QR-кодом. Бронирование имеет ограниченный срок действия, после которого неоплаченная бронь аннулируется. При создании бронирования выполняется проверка доступности мест: система загружает все активные бронирования рейса и сравнивает с вместимостью автобуса. Диаграмма последовательности процесса бронирования и оплаты показана на рисунке 15.
Проектирование базы данных выполняется через PrismaORM^[15]. Нормализация до третьей нормальной формы исключает избыточность данных.

[level2]2.2 Разработка базы данных

Разработка базы данных выполнена на PostgreSQL^[13] с PrismaORM^[15]. Схема включает двенадцать моделей. Модель User — центральная, хранит email (уникальный индекс), хешированный пароль (bcrypt^[2]), имя, телефон, роль (USER, ADMIN, DRIVER, OPERATOR) и флаг isActive для мягкого удаления. Связана с Booking, Favorite, Trip, Chat, Message (таблица 15).
Модель Route содержит наименование, описание, пункты отправления и назначения, расстояние, длительность и стоимость (Decimal). Поле isActive позволяет мягкое удаление маршрутов. Модель Trip представляет рейсы с полями маршрута, времени отправления/прибытия, статусом (SCHEDULED, IN_PROGRESS, COMPLETED, CANCELLED, DELAYED), номером автобуса, водителем и оператором (таблица 16).
Модель Booking хранит бронирования: пользователь, рейс, количество мест, общая стоимость (произведение цены маршрута на места), статус (PENDING, CONFIRMED, CANCELLED, COMPLETED), имя и телефон пассажира. Номера мест вынесены в BookingSeat для нормализации — модель имеет составной уникальный индекс (bookingId, seatNumber) и каскадное удаление. Модель Ticket содержит электронные билеты с QR-кодом (TICKET-<hex>), номером места, флагом isUsed и временем использования. Модель Payment — оплаты с суммой, статусом (PENDING, COMPLETED, FAILED, REFUNDED), методом оплаты и уникальным transactionId. Модель Favorite — избранные маршруты с составным уникальным индексом. Модель Delay — задержки с привязкой к рейсу, причиной и минутами, при создании статус рейса меняется на DELAYED. Модель Bus — госномер, модель, общее количество мест. Модель Chat — чат между водителем и оператором со статусами (WAITING, ACTIVE, CLOSED) и контролем активности через lastHeartbeatAt. Модель Message — сообщения чата с идентификатором отправителя, ролью (DRIVER, OPERATOR, ADMIN) и текстом. Связи между моделями показаны на рисунке 16.
Для целостности данных используются внешние ключи и каскадное удаление. Индексы созданы для email, id маршрута, id пользователя в бронированиях. Миграции управляются через Prisma Migrate — каждая миграция представляет SQL-скрипт с возможностью отката. Начальная миграция создаёт все таблицы, индексы и перечисления.

[level2]2.3 Написание API

Серверный API разработан на NestJS^[10] с модульной архитектурой и TypeScript^[20]. Модуль аутентификации реализует регистрацию (проверка уникальности email, хеширование пароля bcrypt^[2] с фактором 10, генерация JWT^[7]) и вход (верификация пароля, проверка активности аккаунта). При неверных данных возвращается универсальная ошибка без раскрытия причины. JWT-стратегия на Passport.js^[12] извлекает пользователя из токена, гард возвращает null при ошибке аутентификации, позволяя контроллерам обрабатывать отсутствие пользователя самостоятельно.
Модуль маршрутов предоставляет CRUD с мягким удалением (флаг isActive) и поиском по пунктам отправления/назначения (case-insensitive частичное совпадение). Модуль рейсов — управление рейсами с фильтрацией по маршруту и водителю, расчёт доступных мест (разница вместимости автобуса и суммы забронированных мест в статусах CONFIRMED и PENDING). Модуль бронирования создаёт бронирования со статусом PENDING, проверяя доступность мест, поддерживает подтверждение и отмену. Модуль билетов генерирует электронные билеты с криптостойким QR-кодом (randomBytes) и отметкой об использовании. Модуль платежей обрабатывает оплату с генерацией transactionId (TXN-<timestamp>-<random>). Модуль чата — отправка сообщений с логированием и получение истории. Модуль задержек создаёт запись и автоматически обновляет статус рейса на DELAYED. Модуль избранного — добавление и удаление без дублирования. Модуль пользователей — CRUD с фильтрацией по роли, исключение конфиденциальных полей.
Глобальный interceptor логирует каждый запрос (метод, URL, статус, время). Валидация DTO через class-validator^[3], ролевые гарды через декоратор @Roles(). Структура модулей API — в таблице 17.

[level2]2.4 Разработка сайта

Веб-приложение разработано на NextJS^[11] с PrimeReact^[14] и TailwindCSS^[19]. API-слой реализован через Axios^[1] с interceptor, автоматически добавляющим JWT-токен из localStorage к каждому запросу. Слой аутентификации — React^[17] Context с состоянием пользователя, токена и флагов. NextJS middleware (proxy.ts) проверяет аутентификацию и роль на сервере, перенаправляя неавторизованных на страницу входа (с сохранением пути для возврата), а при несоответствии роли — на главную.
Страница каталога маршрутов отображает список доступных направлений в виде карточек с информацией о пунктах отправления и назначения, расстоянии, длительности и стоимости. Каждая карточка содержит кнопку бронирования, при нажатии на которую проверяется аутентификация пользователя. Для неавторизованных пользователей выполняется перенаправление на страницу входа с сохранением текущего маршрута для возврата после авторизации. Каталог маршрутов представлен на рисунке 17.
Страница бронирования представляет собой диалоговое окно, в котором пользователь выбирает конкретный рейс из доступных, указывает количество мест и вводит имя пассажира с номером телефона. Система запрашивает количество доступных мест через API и сравнивает с запрошенным — при недостатке мест отображается предупреждение. После создания бронирования пользователь получает подтверждение с информацией о рейсе и общей стоимости. Страница бронирования показана на рисунке 18.
Страница оплаты отображает детали созданного бронирования: маршрут, дату, количество мест и общую стоимость. Пользователь выбирает метод оплаты, после чего система создаёт запись платежа, обрабатывает оплату через API и подтверждает бронирование. При успешной оплате пользователь получает уведомление о подтверждении. Страница оплаты показана на рисунке 19.
Страница расписания рейсов отображает таблицу со всеми рейсами, их статусами (запланирован, задержан, в пути, завершён, отменён) и цветовой индикацией. Компонент использует PrimeReact DataTable с поддержкой сортировки, фильтрации по дате и маршруту. Пользователь может отслеживать актуальное состояние каждого рейса в реальном времени. Страница расписания показана на рисунке 20.
Панель администратора включает разделы управления маршрутами, рейсами и учётными записями пользователей. Страница управления пользователями отображает таблицу с возможностью поиска, создания, редактирования и удаления записей. Доступ к панели ограничен пользователями с ролью ADMIN на уровне middleware. Панель администратора показана на рисунке 21.
Панель оператора обеспечивает мониторинг активных рейсов, создание записей о задержках, корректировку времени отправления и прибытия, а также создание новых рейсов. При создании задержки оператор указывает причину и длительность, после чего информация автоматически обновляется на всех клиентских устройствах. Панель оператора показана на рисунке 22.
Панель водителя отображает назначенные рейсы с информацией о маршруте, времени и статусе. В нижней части страницы расположен интерфейс чата с оператором, содержащий поле ввода, кнопку отправки и историю переписки. Обновление чата происходит через интервальный опрос сервера для получения новых сообщений. Панель водителя показана на рисунке 23.
Страница профиля пользователя включает вкладки с информацией о бронированиях, электронных билетах и избранных маршрутах. Каждый билет отображается с QR-кодом, который можно предъявить при посадке. Навигация между разделами профиля реализована через PrimeReact TabView. Страница профиля показана на рисунке 24.
Навигационная панель сайта адаптируется в зависимости от роли пользователя: для администраторов отображается ссылка на панель управления, для водителей — на панель водителя, для операторов — на панель оператора. Выпадающие меню управляются через состояние активного элемента, предотвращая одновременное открытие нескольких меню. Структура навигации отражена на рисунке 26.

[level2]2.5 Разработка мобильного приложения

Мобильное приложение разработано на .NET MAUI^[9] с паттерном MVVM^[8] и CommunityToolkitMVVM^[4] для Android и iOS. Приложение ориентировано на пассажиров и взаимодействует с тем же REST API^[18], что и веб-версия, обеспечивая единообразие данных.
ViewModel наследуют BaseViewModel с общими свойствами (IsBusy, ErrorMessage, IsServerOnline). DI-контейнер регистрирует HTTP-клиенты (ApiService, ApiHealthService), сервисы (AuthService, RouteService, BookingService, PaymentService, TicketService, FavoriteService, QrCodeService, OfflineStorageService) и ViewModel со страницами. AuthService управляет JWT^[7]-токеном с хранением в SecureStorage и уведомляет подписчиков через AuthStateChanged.
Модели данных соответствуют контрактам API. SeatItemModel реализует INotifyPropertyChanged для реактивного обновления схемы салона (доступно — зелёный, выбрано — синий, занято — серый).
BookingViewModel реализует четырёхшаговый мастер бронирования: выбор конкретного рейса, указание количества мест с автоматическим пересчётом стоимости, интерактивная схема салона автобуса с цветовой индикацией мест, ввод данных пассажира. Шаги содержат валидацию, пользователь может переключаться между ними как вперёд, так и назад с сохранением введённых данных. После успешного создания бронирования ViewModel переходит в состояние завершения, и пользователю предлагается перейти к оплате. Процесс бронирования в мобильном приложении показан на рисунке 27.
PaymentViewModel загружает информацию о бронировании, предоставляет выбор метода оплаты (банковская карта, СБП, наличные) и обрабатывает платеж через API. При успешной оплате статус бронирования изменяется на CONFIRMED, и система генерирует электронные билеты. TicketViewModel загружает созданные билеты и формирует QR-код для каждого с использованием библиотеки QRCoder^[16] с уровнем коррекции ошибок Q, после чего сохраняет их в офлайн-кэш через OfflineStorageService. Страница электронного билета показана на рисунке 28.
Ключевым преимуществом является поддержка автономного режима. OfflineStorageService кэширует до 10 билетов в JSON-файл, при недоступности сервера загрузка выполняется из кэша. ApiHealthService проверяет доступность сервера и переключает режимы онлайн/офлайн через событие ConnectivityChanged.
Навигация между страницами приложения организована через Shell-навигацию .NET MAUI^[9] с TabBar, содержащим вкладки «Главная» и «Профиль». Дополнительные маршруты (login, register, booking, payment, ticket) зарегистрированы через Routing.RegisterRoute и доступны для программной навигации с передачей параметров через QueryPropertyAttribute. Пользовательский интерфейс каждой страницы описан в XAML с привязкой данных к ViewModel и использованием конвертеров (StatusToColor, StatusToText, PriceFormat). Единая цветовая палитра и стили элементов управления централизованно заданы в файлах Colors.xaml и Styles.xaml. Страница профиля пользователя показана на рисунке 29.
Главная страница мобильного приложения предоставляет доступ к поиску маршрутов по пунктам отправления и назначения, отображению списка доступных направлений и мониторингу доступности сервера. При потере соединения пользователь получает предупреждение об ограничении функциональности. Интерфейс главной страницы выполнен в едином стиле с веб-приложением. Главная страница мобильного приложения с поиском маршрутов показана на рисунке 30.
Приложение реализует полный цикл обслуживания: от поиска маршрута до предъявления QR-кода при посадке, включая автономный режим для критически важной функции доступа к билетам без интернета.

[level1]ВЫВОД ПО ПРАКТИЧЕСКОЙ ЧАСТИ

В практической части рассмотрены этапы проектирования и разработки информационной системы «АВ-Вокзал». Проектирование выполнено на основе трёхзвенной клиент-серверной архитектуры с REST API^[18], ролевой моделью доступа на четыре роли и двухуровневой проверкой прав (серверная через JWT-гарды, клиентская через NextJS middleware). Спроектированы процессы аутентификации, бронирования, оплаты, чата и отслеживания задержек.
Разработана база данных PostgreSQL^[13] с двенадцатью моделями и нормализацией до третьей нормальной формы. Реализован серверный API на NestJS^[10] с модулями аутентификации, маршрутов, рейсов, бронирования, билетов, платежей, чата, задержек, избранного и пользователей. Создано веб-приложение на NextJS^[11] с PrimeReact^[14] для всех ролей. Разработано мобильное приложение на .NET MAUI^[9] с пошаговым мастером бронирования, онлайн-оплатой, генерацией QR-кодов и поддержкой автономного доступа к электронным билетам.
Практическая реализация подтверждает работоспособность выбранной архитектуры и технологического стека. Система обеспечивает полный цикл обслуживания пассажиров — от поиска маршрута до предъявления электронного билета при посадке — и предоставляет инструменты оперативного управления для персонала автовокзала.
